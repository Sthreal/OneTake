# AGENTS.md · One Take 项目协作规则

> 本文件是 **One Take 项目级工作规则**。任何在本目录（One Take）内工作的 AI 助手或协作者都必须遵守。
> 规则的来源：项目负责人（用户）在本项目开发过程中明确提出的要求。

---

## 一、每次动代码前，必须先给方案

方案正文固定包含这 6 块：

1. **目标** —— 这次要解决什么问题
2. **边界** —— 做什么、明确**不做什么**
3. **切片** —— 按「接口 → 逻辑 → 工具 → 返回 → 测试」拆成可独立验证的切片
4. **涉及文件** —— 新增哪些、修改哪些
5. **验收标准** —— 可量化（能测、能查、能看），不许写"感觉好了"
6. **待拍板参数** —— 需要用户确认的具体数值或取舍

**未得到用户确认前，不得动手改代码。**

---

## 二、每个方案必须附带「总结」（固定 8 段，顺序和标题不许变）

| # | 段落 |
|---|---|
| ① | 解决了什么 |
| ② | 怎么实现的 |
| ③ | 具体的实现方式 |
| ④ | 为什么选择这种方式 |
| ⑤ | 有没有其他方式 |
| ⑥ | 为什么不选其他方式 |
| ⑦ | 这种方式的难点是什么 |
| ⑧ | 怎么能克服这种难点 |

> 第 ⑤⑥ 段必须真的列出备选方案和淘汰理由，**不允许只写"没有其他方式"**。

**方案必须落档**：每个新切片的完整方案（目标 / 边界 / 步骤 / 涉及文件 / 验收标准 / 待拍板项 + 8 段总结）要写进 `docs/方案档案.md` 的对应小节，**不允许只留一行要点**；完成后再在文末「变更记录」追加一行。

---

## 三、开发约定

- 每加一个功能，走完「**接口 → 逻辑 → 工具 → 返回 → 测试**」才算一个切片
- **每个切片完成后项目必须仍然能运行**：`pytest` 全绿 + 服务可启动
- 改动不得影响其他功能：改前跑基线，改后跑全量回归，并列出受影响的调用方
- 每个切片独立提交，可单独回滚
- 把**错误处理、安全、日志当成功能**来做：参数校验 / 工具异常捕获 / 最大轮数 / 重复调用降级 / 敏感操作白名单 / 日志记录 / API Key 只放 `.env` 不进 Git
- **绝不执行用户未明确要求的删除操作**

---

## 四、交付与展示

- 任何改动（代码、文档、讲解稿）**先让用户看效果，用户确认后**才提交或推送
- **不擅自 push GitHub**，推送前必须得到用户明确同意
- 文档、分析、清单类内容默认**只在聊天框展示**；用户说"存下来"才落盘
- git 提交信息用中文 + 类型前缀：`feat` / `fix` / `docs` / `test` / `chore`
