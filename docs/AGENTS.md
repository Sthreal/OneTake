# AGENTS.md · One Take 项目协作规则

> 本文件是 **One Take 项目级工作规则**。任何在本目录（One Take）内工作的 AI 助手或协作者都必须遵守。
> 规则的来源：项目负责人（用户）在本项目开发过程中明确提出的要求。

---

## 一、每次动代码前，必须先给方案

方案正文固定包含这 6 块：

1. **目标** —— 这次要解决什么问题
2. **边界** —— 做什么、明确**不做什么**
3. **切片** —— 按「接口 → 逻辑 → 工具 → 返回 → 测试」拆成可独立验证的切片
4. **涉及文件** —— 新增哪些、修改哪些
5. **验收标准** —— 可量化（能测、能查、能看），不许写"感觉好了"
6. **待拍板参数** —— 需要用户确认的具体数值或取舍

**未得到用户确认前，不得动手改代码。**

---

## 二、每个方案必须附带「总结」（固定 8 段，顺序和标题不许变）

| # | 段落 |
|---|---|
| ① | 解决了什么 |
| ② | 怎么实现的 |
| ③ | 具体的实现方式 |
| ④ | 为什么选择这种方式 |
| ⑤ | 有没有其他方式 |
| ⑥ | 为什么不选其他方式 |
| ⑦ | 这种方式的难点是什么 |
| ⑧ | 怎么能克服这种难点 |

> 第 ⑤⑥ 段必须真的列出备选方案和淘汰理由，**不允许只写"没有其他方式"**。

**方案必须落档**：每个新切片的完整方案（目标 / 边界 / 步骤 / 涉及文件 / 验收标准 / 待拍板项 + 8 段总结）要写进 `docs/方案档案.md` 的对应小节，**不允许只留一行要点**；完成后再在文末「变更记录」追加一行。

---

## 三、开发约定

- 每加一个功能，走完「**接口 → 逻辑 → 工具 → 返回 → 测试**」才算一个切片
- **每个切片完成后项目必须仍然能运行**：`pytest` 全绿 + 服务可启动
- 改动不得影响其他功能：改前跑基线，改后跑全量回归，并列出受影响的调用方
- 每个切片独立提交，可单独回滚
- 把**错误处理、安全、日志当成功能**来做：参数校验 / 工具异常捕获 / 最大轮数 / 重复调用降级 / 敏感操作白名单 / 日志记录 / API Key 只放 `.env` 不进 Git
- **绝不执行用户未明确要求的删除操作**

---

## 四、交付与展示

- 任何改动（代码、文档、讲解稿）**先让用户看效果，用户确认后**才提交或推送
- **不擅自 push GitHub**，推送前必须得到用户明确同意
- 文档、分析、清单类内容默认**只在聊天框展示**；用户说"存下来"才落盘
- git 提交信息用中文 + 类型前缀：`feat` / `fix` / `docs` / `test` / `chore`

## 五、Bug 修复工作流（强制）

### 总体原则

1. **不猜测**：所有判断必须有依据（代码、日志、文档、可复现实验），依据不足时先提问。
2. **最小改动**：只修导致 Bug 的根因，不顺手重构、不美化无关代码。
3. **对症下药**：区分“症状”和“根因”，优先消除根因；若只能缓解症状，必须明确说明。
4. **回归优先**：任何修改都要评估对现有功能、依赖方、边界条件的影响。
5. **风格一致**：修改后的代码遵循项目现有的命名、格式、错误处理模式，不另起炉灶。
6. **可解释**：每一步改动都能说清“为什么这样改”以及“为什么不改别的”。

### 第一步：理解问题（先确认，再动手）

- 用一两句话复述理解的 Bug 现象，等待用户确认或纠正。
- 主动收集以下信息，缺失时明确提问，不要自行假设：
  - 复现步骤与触发条件（何时出现、是否必现）
  - 错误信息/堆栈日志全文
  - 运行环境（系统、语言/框架版本、依赖版本）
  - 期望行为 vs 实际行为
- 若用户要求直接分析，则基于已有材料列出“已知事实”与“待确认假设”，分别标注。

### 第二步：定位根因

- 先尝试复现或推演问题路径，再下结论。
- 检查优先级：边界条件与空值 → 类型/编码问题 → 并发与状态 → 资源生命周期（连接、句柄、定时器）→ 逻辑分支遗漏 → 数据格式假设错误。
- 若项目有版本管理，对比相关代码的最近变更（git diff / blame），优先怀疑最近改动。
- 给出根因时，引用具体代码位置和证据链（哪一行、什么条件下出错、为什么）。

### 第三步：设计方案

- 列出可选方案（至少考虑 2 个），比较改动范围、风险、可维护性后给出推荐，并说明理由。
- 优先选择：改动最小、风险最低、与现有架构一致的方案。
- 明确该修改会影响的模块、函数、调用方；若存在回归风险，主动提示。
- 涉及删除、替换接口、改变行为等有风险操作时，先说明影响再征求确认。

### 第四步：实施修复

- 只修改与根因相关的代码，不顺手“优化”无关部分。
- 修改后，同步检查并更新受影响的测试（单元测试、边界用例、原有断言）。
- 如修复涉及多文件，按依赖顺序说明每个文件的改动目的。
- 不引入新的未解释魔法值；注释只解释“为什么”，不解释“是什么”。

### 第五步：验证与交付

- 提供明确的验证方法：可运行的测试命令、手动复现步骤、或需要用户确认的行为点。
- 检查边界：空输入、极限值、并发、重复调用、异常路径是否都已覆盖。
- 交付时按以下格式输出：

【Bug 现象】  
【根因】证据链 + 代码位置  
【修复方案】为何选此方案  
【代码变更】文件、函数、改动说明（可含 diff）  
【影响范围】受影响的模块与潜在风险  
【验证方式】测试命令 / 复现步骤 / 期望结果  
【遗留问题】未覆盖的场景或需进一步确认的点

### 红线

- 禁止静默修改用户没要求改的代码；确有必要时先提出并说明理由。
- 禁止在未验证的情况下声称“已修复”；无法验证时要如实说明。
- 禁止用删除功能、绕过检查、硬编码等方式掩盖问题。
- 禁止在缺少关键信息时编造错误原因或修复方案。
- 修改涉及数据、资金、安全相关逻辑时，额外标注风险并建议补充测试。
