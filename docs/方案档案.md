建立第一个可独立运行、可验证、可回滚的业务垂直切片：

```text
HTTP API
→ Project 应用服务
→ PostgreSQL project Schema

→ API 返回
→ 自动化测试
```

## 八段总结

### ① 解决了什么

解决“项目”这个核心概念从无到有的问题，并建立第一条 API、领域、数据库和 Outbox 可靠写入链路。

### ② 怎么实现的

采用模块化单体结构，`project` 负责项目和用例，`outbox` 负责事件落库。API 只负责协议转换，业务规则在 `domain`，事务和用例在 `application`，数据库实现放在 `adapters`，模块之间只通过 `public.py` 暴露能力。

### ③ 具体的实现方式

新增 `project` 与 `outbox` 模块。创建项目时，Project 服务和 Outbox 服务共享同一个 SQLAlchemy 事务。Alembic 创建 `project.projects` 与 `outbox.outbox_events`。API 使用 `/api/v1/projects`，请求中间件生成 `request_id`，异常统一转换为领域错误响应。

### ④ 为什么选择这种方式

该方式满足“一个概念一个模块”和“改一个功能不影响其他功能”。项目和 Outbox 分属独立模块，事务内写入避免项目和事件不一致，Alembic 管理长期数据库变更，公开接口防止模块内部互相侵入。

### ⑤ 有没有其他方式

有其他方式：

- 使用 `Base.metadata.create_all()` 自动建表。
- 将全部逻辑写在 `main.py` 或单个 `services.py`。
- 创建项目后直接发送事件，不使用 Outbox。
- 使用原始 UUID，不添加业务前缀。
- 只使用内存存储，不接 PostgreSQL。
- 将 Project 拆成独立微服务。

### ⑥ 为什么不选其他方式

- `create_all()` 无法可靠管理后续数据库变更。
- `main.py` 或 `services.py` 会破坏一个概念一个模块。
- 直接发事件可能导致项目存在但事件丢失。
- 原始 UUID 不利于日志追踪和外部接口辨识。
- 内存存储在服务重启后丢数据。
- 微服务对当前单机 MVP 过重，会增加网络、部署和调试成本。

### ⑦ 这种方式的难点是什么

- Docker 启动时可靠执行数据库迁移。
- 保证项目与 Outbox 同事务提交。
- 防止模块通过内部文件互相导入。
- 集成测试中隔离 PostgreSQL 和其他依赖。
- 保持现有 M0 服务和前端不回归。

### ⑧ 怎么能克服这种难点

- 在 Compose 中增加一次性 `migrate` 服务，API 和 Worker 等待迁移完成。
- 在同一个 SQLAlchemy Session 中写入 Project 和 Outbox。
- 使用 `public.py` 和导入检查限制模块边界。
- 使用独立测试数据库并回滚测试事务。
- 改动前运行健康基线，改动后运行 pytest、Compose 和健康检查。
- 每个切片独立提交，保留回滚点。

## M1-02：素材注册与 MinIO 直传基线

### 状态

- 用户确认：是
- 实施状态：已完成
- 切片类型：后端垂直切片

### 一、目标

实现浏览器直接向 MinIO 上传商品图片，并在 PostgreSQL 中可靠登记素材：

```text
申请上传
→ 浏览器直传 MinIO
→ 完成上传
→ 服务端复核文件
→ 登记 Asset
→ 写入 AssetRegistered 事件
→ 查询素材列表
```

### 二、边界

本次要做：

- 新增 `asset` 模块。
- 新增 `object_storage` 集成模块。
- 新增 `asset.assets` 表。
- 支持 JPG、PNG、WebP。
- 支持同项目最多 5 张。
- 使用 MinIO 预签名 URL 直传。
- 完成上传后由服务端验证对象、大小、SHA-256、格式和尺寸。
- 写入 `AssetRegistered` Outbox 事件。
- 提供素材列表接口。
- 配置 MinIO CORS。
- 增加单元、集成和 API 契约测试。

- 前端上传页面。

### 三、切片

#### 1. 接口


预签名请求：

```json
{
  "original_filename": "product.png",
  "mime_type": "image/png",
  "size_bytes": 2450123,
  "sha256": "optional-client-sha256",
  "width": 1200,
  "height": 1200
}
```

预签名响应包含：

- `asset_id`
- `object_key`
- `upload_url`
- `expires_at`
- `required_headers`
- `request_id`

- `original_filename`
- `mime_type`
- `size_bytes`
- `sha256`
- `width`
- `height`

- `asset_id`
- `project_id`
- `status=ready`
- `mime_type`
- `size_bytes`
- `width`
- `height`

#### 2. 逻辑

## 八段总结

### ① 解决了什么

解决商品图片从浏览器进入系统并成为可追踪 Asset 的问题，为识别和主图处理提供稳定输入。

### ② 怎么实现的

使用 `asset` 模块管理素材生命周期，使用 `object_storage` 集成模块封装 MinIO。浏览器通过预签名 URL 直传，API 在完成阶段重新验证文件，并通过 Outbox 写入 `AssetRegistered`。

### ③ 具体的实现方式

预签名接口创建 `pending` Asset，返回短期 PUT URL。浏览器直接上传 MinIO。完成接口读取对象、校验大小和 SHA-256、用 Pillow 验证格式与尺寸，更新 Asset 为 `ready`，并在同一事务写 Outbox。

### ④ 为什么选择这种方式

直传避免大文件经过 FastAPI。服务端复核不信任客户端声明。独立 Asset 模块和存储 Adapter 保证修改 MinIO、上传策略或图片规则时不会影响 Project 和 Outbox。

### ⑤ 有没有其他方式

有其他方式：

- FastAPI 接收 multipart 后转发到 MinIO。
- 先上传临时目录，再后台同步。
- 完全信任浏览器提供的尺寸和摘要。
- 使用本地文件系统。
- 上传完成后再创建 Asset。
- 在 Asset 服务中直接使用 MinIO SDK。

### ⑥ 为什么不选其他方式

- API 中转大文件会占用内存和请求时间。
- 临时目录增加一致性和清理问题。
- 信任客户端无法保证文件真实性和安全性。
- 本地文件不适合多 Worker。
- 不保留 `pending` 会产生孤儿文件。
- 直接使用 MinIO SDK 会形成强耦合。

### ⑦ 这种方式的难点是什么

- 预签名 URL 的 Host 必须对浏览器可访问。
- 流式计算 SHA-256 和读取图片要避免多次传输。
- CORS 必须允许浏览器 PUT。
- 并发上传不能突破 5 张限制。
- 素材状态和 Outbox 必须同事务。
- Pending 文件需要后续清理入口。

### ⑧ 怎么能克服这种难点

- 内部使用 `minio:9000`，签名 URL 使用 `MINIO_PUBLIC_ENDPOINT`，测试通过依赖覆盖使用内部地址。
- 在同一个对象流中计算哈希并交给 Pillow 解析。
- 使用 MinIO CORS 配置明确来源、方法和请求头。
- 在事务内检查数量，并增加数据库唯一约束。
- Asset 状态和 Outbox 使用同一 SQLAlchemy Session。
- M1-03 再实现过期清理。

## 八段总结

### ① 解决了什么

解决 M1-02 只有 API、没有产品化操作界面的问题，并把前端视觉统一为苹果风、Codex 桌面端式的专业 SaaS 工作台。

InputWorkspace 负责页面结构，useProjectWorkspace 管理项目，useAssetUploads 管理上传队列，validation.ts 负责本地校验，styles.css 定义颜色、圆角、阴影、玻璃和响应式规则。

### ④ 为什么选择这种方式

它同时满足苹果风、高信息密度和专业 SaaS 要求，并保持一个概念一个模块。视觉变量集中管理，修改颜色、圆角或布局不会影响上传逻辑。

### ⑤ 有没有其他方式

- 使用 Ant Design 或 MUI。
- 使用 Tailwind 和现成组件库。
- 单列表单页面。
- 大量玻璃、渐变和动画。
- 直接复制 Codex 界面。
- 深色主题优先。

### ⑥ 为什么不选其他方式

- 重型组件库风格容易偏离苹果感。
- 单列页面不适合 Codex 式专业工作台。
- 大面积玻璃和动画会显得花哨，也影响性能。
- 直接复制 Codex 会缺乏 One Take 自己的产品识别。
- 深色模式不是当前必须项，会增加首版设计成本。

### ⑦ 这种方式的难点是什么

- 苹果风与专业 SaaS 密度之间的平衡。
- 玻璃效果在小屏和低性能设备上的表现。
- 三栏布局的响应式折叠。
- 上传进度与 React 状态同步。
- 刷新恢复时避免显示旧数据。
- 保持视觉克制但不能过于像普通后台模板。

### ⑧ 怎么能克服这种难点

- 使用中性色为主，蓝色只用于关键操作和状态。
- 玻璃只用于固定区域，正文使用实体表面。
- 明确三档响应式布局，优先保证上传操作。
- 上传控制与展示组件分离。
- 项目 ID 只作恢复线索，项目详情始终重新向后端读取。
- 用设计 Token 和少量基础组件统一风格，不堆叠装饰效果。

## 八段总结

### ① 解决了什么
解决主图链路虽然已有真实 Adapter，但尚未完成真实请求校验、配置前置检查和可验证联调的问题。

### ② 怎么实现的
在现有 Port/Adapter 架构上加固 Qwen Image Edit 和 Photoroom，添加配置预检、图片响应校验、失败隔离、日志和 Fake HTTP 测试。

### ③ 具体的实现方式
Worker 从 MinIO 读取选中素材，依次调用图像编辑 Provider、去背 Provider 和 Pillow 标准化，成功后才写入新主图版本。

### ④ 为什么选择这种方式
保持既有 Pipeline 和前端契约不变，只替换 Provider 适配器，改动范围最小，能单独回滚。

### ⑤ 有没有其他方式
在服务中直接写 Qwen/Photoroom 请求、自动回退 Mock、同步 API 调用或一次性替换全部 Provider。

### ⑥ 为什么不选其他方式
会破坏模块边界、掩盖真实失败、造成 API 超时，并扩大联调故障范围。

### ⑦ 这种方式的难点是什么
真实供应商请求格式、返回内容不稳定、透明通道、超时、配额、费用和失败后的版本一致性。

### ⑧ 怎么能克服这种难点
保留 Mock 基线、Fake HTTP 回归、严格图片校验、真实调用前预检、单 Provider 开关、无自动回退和人工费用确认。
