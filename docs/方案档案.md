## 切片 A · 钩子 / CTA 硬规则 + hook_library 扩库

> 状态：已实现。Owner 确认 P1–P8 均为推荐 A。本档只覆盖切片 A（P4A、P5A 及钩子库、3 秒入画）。

### 1. 目标

在不改前端、不改 Meta 投放、不重做 Wan i2v 的前提下，让口播内容层具备可测的转化硬规则：禁套话开场、前 3 秒钩子、45–72 字内的双 CTA、短版中段续命，以及信任/社证方向的画面钩子。商品在第 2 镜结束时已经入画。

### 2. 边界

**做**

- `normalize_generated` 对套话开场、钩子停拇指、双 CTA 失败，并在错误信息里标明规则名和维度。
- 生成 prompt 与审稿 prompt 共用同一段契约。审稿仍是可选增强，不改闸门。
- `hook_library` 从 6 条扩到 11 条。新条目是画面指令，不改写用户口播，不编造销量或可读评价。
- 规则分镜：第 1 镜仍可 `absent` 铺垫；第 2 镜 `end ≤ 3.0` 且 `product_mode != absent`；第 3 镜（usage）写入续看画面约束。总时长仍是 14 秒。

**不做**

- 任何 `platform/**/web/**`、`.tsx` / `.jsx` / `.css`。
- 多角度 `candidates`、`SCRIPT_REVIEW_GATE`、等长 ±20%、video 入口 409。
- 运动提示词重写、Wan 算法重写、Meta 投放。
- 真实付费 provider 调用。校验与单测走 Mock / 规则函数。

### 总结

#### ① 解决了什么

口播可以「大家好」开场，画面要到第 6 秒才稳定入商品，短版中段没有续看理由，钩子库只有 6 条且没有信任/社证方向。这些都不可测。

#### ② 怎么实现的

文案规则做成纯函数，挂在已有的 `normalize_generated` 上。画面规则改 `BEATS` 与钩子库，不改 i2v 实现。

#### ③ 具体的实现方式

- 黑名单按开场前缀匹配，后文里的「大家好」不算。
- 钩子：去标点至少 8 字，且含问号/叹号或「还在」「为什么」「别再」「难道」等词。
- 双 CTA：场景句以「顺手看看」一类轻提结尾，`cta` 含看看/链接/下单/带走等行动词。Mock 模板同步改成这个形状。
- 分镜：0–1s 空镜铺垫，1–3s 商品 overlay，3–10s 使用镜并追加续看画面句，10–14s CTA。使用镜 7 秒由既有分段计划按 5 秒上限拆开，总秒数不变。
- 钩子库新增 h7–h11（熟练的手、使用痕迹、共享桌面、二次伸手、空白便签）。便签钩子明确不给可读文字。

#### ④ 为什么选择这种方式

规则放在归一化出口，生成、手改、审稿回退都经过同一道门。错误码沿用 `SCRIPT_GENERATION_ERROR`，自动链对生成失败的重试语义不用改。画面钩子继续「只指挥镜头、不改口播」。

#### ⑤ 有没有其他方式

1. 把套话只写进审稿 prompt，归一化不拒绝。
2. 放宽字数上限到 90 来塞双 CTA。
3. 把第 1 镜直接改成商品特写，取消空镜铺垫。
4. 为了不增加 Wan 调用次数，把总时长缩到 13 秒以内，让四镜都 ≤5 秒。

#### ⑥ 为什么不选其他方式

1. prompt 挡不住 Mock 和手改，验收要求归一化可失败。
2. P4A 已经否决放宽到 90。
3. 现有测试和素材策略都依赖开场空镜；拍板是「第 2 镜入画」，不是取消铺垫。
4. 成片终点被锁在 14 秒，用来对齐短版口播。前两镜合计 ≤3 秒之后，后两镜要装下 11 秒，四镜结构下必然有一镜超过 5 秒。缩总时长会让口播和画面错位。

#### ⑦ 这种方式的难点是什么

45–72 字里要同时放下钩子、卖点和两处 CTA。3 秒入画会让使用镜变成 7 秒，分段调用从 4 次变成 5 次，费用预估必须跟着变，否则审批金额和真实调用不一致。

#### ⑧ 怎么能克服这种难点

双 CTA 用「场景末尾四个字 + 短末句」，不新加一段广告。Mock 与单测稿都卡在 45–72 内。预估继续读同一张 `BEATS`，单测把调用次数改成 5、总秒数仍是 14。空镜从 3 秒变成 1 秒后，免 Key 素材扣掉的也是这 1 秒。

## 切片 B · 多脚本角度（≥3 套可选用）

> 状态：已实现。Owner 确认 P1–P8 均为推荐 A。本档只覆盖切片 B（P2A / P3A / P7A）。
> 切片 A（钩子 / CTA）在独立 PR。切片 C（`SCRIPT_REVIEW_GATE` / review apply）本切片不做。

P3A 原文的第三角占位是 `diff_or_trust`。P2A 已把第三角定名为「对比测评」，任务书指定标识 `comparison`，且只作文案角度。本切片按这个标识实现，不接受请求体改列表。

### 1. 目标

一次 `generate` 产出 3 套可选用口播（痛点种草 / 场景安利 / 对比测评），调用方可以选其中一套作为当前稿再确认。旧客户端不看候选时，仍然拿到角 0。

### 2. 边界

**做**

- 固定三角：`pain_point`、`scene`、`comparison`。
- 同一 `generation_batch_id` 下插 3 条 `ScriptVersion`，角度和选中标记放进已有 `facts` JSON。

- Mock 按角度改 hook 和场景句。真实 Qwen 只在传入 `angle` 时把角度说明接到 prompt 末尾，本切片不发 live 请求。
- `confirm` 只确认当前选中稿。content_plan 仍通过 latest 要求文案已确认。

**不做**

- 任何 `platform/**/web/**`。
- `SCRIPT_REVIEW_GATE`、`review` / `apply`、等长 ±20%、video 入口 409。
- 改 `hook_library`、`content_plan/generator` 的入画规则，或把 `comparison` 写进画面 style。
- 新表、新列、付费调用。

### 总结

#### ① 解决了什么

一次生成只落一条口播，后面的分镜只能拿这一条去切画面。调用方没法在痛点、场景、对比三种说法里选。

#### ② 怎么实现的

同一次 generate 插入 3 条脚本版本，用 facts 里的批次号和角度记在一起。接口把候选一并返回，select 改选中标记，latest 和 confirm 都跟着选中那条走。

#### ③ 具体的实现方式

`angles.py` 固定三角和 prompt 句子。`request` 为一批分配连续 version_number，角 0 的 `facts.selected=true`。一个 script job 按角度各生成一次，全部成功才一起标 ready；有一条失败则整批 failed。`repository.latest` 读最新一批的选中条，所以角 0 即使 version_number 最小也是旧客户端看到的那条。Mock 的 scene / comparison 用不同 hook 和场景句；Qwen 只在传入 angle 时把「仅文案、禁止画面风格」接到 prompt 末尾。

#### ④ 为什么选择这种方式

facts JSON 已经存在，角度和批次放进去就不用迁移。响应多两个字段，`version` 仍是选中稿，旧前端可以不改。对比测评只出现在文案角度上，分镜风格表保持原样，合规禁令不用放宽。

#### ⑤ 有没有其他方式

1. 新表或 `candidates` JSON 列，一条版本里塞三套稿。
2. 把第三角做成 content_plan 的 comparison 画面风格。
3. 允许请求体传入 3–5 个自定义角度。
4. 和切片 A 合成一个 PR，直接改 hook 库和入画规则。

#### ⑥ 为什么不选其他方式

1. P7A 明确少迁移；新列要动 alembic，和「不加表」相反。
2. comparison / 对比测评已经在 `AI_REVIEW_STYLES` 里，写进画面风格会稳定触发合规警告。
3. P3A 是固定三角，自定义列表是另一个选项。
4. 切片 A 已有独立 PR，钩子库和入画不该在这个分支上再改一遍。

#### ⑦ 这种方式的难点是什么

以前 latest 等于最大 version_number。一批里角 0 的号最小，如果还按最大号取，旧客户端会拿到对比测评而不是痛点稿。select 之后还要保证 confirm 和 content_plan 不会误用另外两条。和切片 A 会同时改 mock、Qwen prompt 和 `service.py`。

#### ⑧ 怎么能克服这种难点

latest 改为「最新一批的选中条」，`next_version_number` 仍看最大号，避免第二批撞唯一约束。confirm 先检查选中标记。content_plan 继续只读 latest，不读候选。本分支不改 generator / hook_library；重叠文件限制在多角度存储和 prompt 后缀，rebase #14 时保留两边。

## 切片 C · 花钱前审稿闸门

> 状态：已实现。Owner 确认 P1–P8 均为 **A**。本文件只覆盖切片 C（P1A、P6A）。
> 切片 A（钩子 / CTA）与切片 B（多角度候选）在并行 PR 里，不在本分支。
> 合并顺序若是 A 或 B 先落地，本文件会和它们的 `docs/方案档案.md` 冲突：请保留各切片小节，不要互相覆盖。

### 如何过审稿闸

默认 `SCRIPT_REVIEW_ENABLED=true`、`SCRIPT_REVIEW_GATE=enforce`。付费视频入口在费用审批之前先看这道闸。

1. 文案生成到 `ready`（自动链代确认过的 `confirmed` 稿也可以审）。
2. `POST /api/v1/projects/{project_id}/script/review`  
   对**当前 latest 稿**跑既有四维：`rhythm` / `spoken` / `freshness` / `structure`。  
   响应里的 `gate_status=reviewed` 只表示审完了，**还没过闸**。`failed` 表示这次审稿不能当成功。
3. `POST /api/v1/projects/{project_id}/script/review/apply`  
   - `{"action":"apply"}`：等长和全文校验都通过时，写入改写。  
   - `{"action":"ack"}`：明确保留原稿。等长失败、内容校验失败、审稿调用失败，都只能走 ack。
4. `gate_status=passed` 之后，`POST /script/confirm` 才允许确认。付费 `POST /video`、`/compose`、`/video/batch`、分段候选、返修、关键帧候选才不再因审稿被拒。
5. 过了审稿闸仍要过 `cost_approvals`。两道闸都在付费 provider 之前。未过审稿闸时这些入口返回 **409** `SCRIPT_REVIEW_REQUIRED`，付费 provider 调用次数为 0。
6. 手改文案会清掉闸门，必须重新 review，再 apply 或 ack。
7. `SCRIPT_REVIEW_GATE=off` 不拦截。`warn` 不拦截，只打日志。`enforce` 是默认。

等长规则（P6A）：每个被改写的字段（`hook`、`pain_point`、`usage_scenario`、`cta`、每一条 `selling_points`）去掉标点后的字数相对原稿 **±20%**，全文口播仍是 **45–72**。任一不满足，整次 review 记为失败，不能 apply，也不能静默当成已经过闸。人要继续，必须 ack 原稿。

自动链可以代按「文案已确认」，但**不会**替人 ack 审稿闸。因此自动链跑完后，付费视频仍然 409，直到有人 apply 或 ack。

### 1. 目标

口播进付费视频之前，必须先走过显式审稿：四维结果给人看，等长改写可以应用，或者人明确保留原稿。未完成这一步时，付费视频入口拒绝，且不调用付费 provider。现有费用审批表不改。

### 2. 边界

**做**

- 配置默认：`SCRIPT_REVIEW_ENABLED=true`，`SCRIPT_REVIEW_GATE=off|warn|enforce` 默认 `enforce`。
- `POST .../script/review` 与 `POST .../script/review/apply`。
- 复用 `REVIEW_DIMENSIONS = rhythm/spoken/freshness/structure`。
- 等长 ±20% 与全文 45–72。失败整次不算过闸（P6A）。
- `MockScriptAdapter.review()` 可配置，单测不打真实模型。
- 六个付费视频入口在费用闸之前检查审稿闸。
- 闸门状态放进既有 `script.versions.facts.review_gate`，不加表。

**不做**

- 任何 `platform/**/web/**`。
- 多角度 candidates（切片 B）、钩子库扩容和套话硬规则（切片 A）。
- 替换或改写 `cost_approvals`。
- 真实付费 provider 调用。
- 自动链替人 ack。

### 总结

#### ① 解决了什么

生成完口播就可以直接花钱做视频。原来的 `SCRIPT_REVIEW` 默认关闭，失败还会静默退回原稿并当成生成成功，拦不住付费入口。

#### ② 怎么实现的

在现有四维审稿上加显式 review / apply，把闸门状态放进 `facts`，付费视频入口在费用闸之前检查。等长不通过就整次失败，只允许人保留原稿。

#### ③ 具体的实现方式

- 配置两个开关：是否启用审稿，以及 `off|warn|enforce`。
- `enforce` / `warn` 时，生成任务不再自动调用审稿，避免降级被当成过闸。`off` 且启用时，仍走原来的增强降级。
- 审稿结果写入 `facts.review_gate`，并用当前口播指纹绑定。手改文案会清掉记录。
- apply 在服务端再跑一遍 ±20% 和 `normalize_generated`。通过才改稿；改了已确认稿则退回 `ready`。
- ack 不改字，只把当前指纹标成 passed。没先 review 不能 ack。
- 六个付费路由先看预估是不是付钱。免费 / mock 不拦。付钱且未 passed：enforce 返回 409，warn 记日志。没有视频方案时与费用闸一样交给原入口报「方案不存在」。
- 自动链 `confirm(..., enforce_review_gate=False)`，不写 passed。

#### ④ 为什么选择这种方式

闸门是文案态，不是另一张钱表。费用审批继续按 `payload_hash` 绑预估。少迁移：状态塞进已有 JSON。Mock 可配置，单测能证明 0 次付费构造。

#### ⑤ 有没有其他方式

1. 只把 `SCRIPT_REVIEW_ENABLED` 改成 true，继续在生成时自动改写并静默降级。
2. 等长失败时自动丢掉超长字段、保留原句，并当作审稿成功。
3. 新表存审稿记录和闸门状态。
4. 自动链在确认文案时自动 ack，让一键流程直接能开视频。

#### ⑥ 为什么不选其他方式

1. 静默降级正是现在拦不住付费的原因。P1A 要求花钱前有人点过。
2. P6A 明确否决自动丢字段。失败必须人 ack。
3. 现有 `facts` 够用，不必为闸门加迁移。
4. 自动 ack 等于机器替人过闸，付费视频会在没有人看稿的情况下放行。

#### ⑦ 这种方式的难点是什么

enforce 会打断「生成完直接确认 / 直接开视频」，也会让自动链如果在 `confirm()` 里硬拦就停在文案。等长和 45–72 要同时成立。并行的切片 A/B 会改同一批 script / adapter 文件。

#### ⑧ 怎么能克服这种难点

确认接口默认拦截，自动链显式关掉拦截但不写 passed，付费入口仍然拦截。等长用口播字数（去标点）计算，全文继续走 `normalize_generated`。本 PR 只加审稿闸门；rebase 时保留 A 的钩子规则和 B 的角度候选，审稿对象始终是 latest 稿。
