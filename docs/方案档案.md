## 八段总结

### ① 解决了什么

解决“项目”这个核心概念从无到有的问题，并建立第一条 API、领域、数据库和 Outbox 可靠写入链路。

### ② 怎么实现的

采用模块化单体结构，`project` 负责项目和用例，`outbox` 负责事件落库。API 只负责协议转换，业务规则在 `domain`，事务和用例在 `application`，数据库实现放在 `adapters`，模块之间只通过 `public.py` 暴露能力。

### ③ 具体的实现方式

新增 `project` 与 `outbox` 模块。创建项目时，Project 服务和 Outbox 服务共享同一个 SQLAlchemy 事务。Alembic 创建 `project.projects` 与 `outbox.outbox_events`。API 使用 `/api/v1/projects`，请求中间件生成 `request_id`，异常统一转换为领域错误响应。

### ④ 为什么选择这种方式

该方式满足“一个概念一个模块”和“改一个功能不影响其他功能”。项目和 Outbox 分属独立模块，事务内写入避免项目和事件不一致，Alembic 管理长期数据库变更，公开接口防止模块内部互相侵入。

### ⑤ 有没有其他方式

有其他方式：

- 使用 `Base.metadata.create_all()` 自动建表。
- 将全部逻辑写在 `main.py` 或单个 `services.py`。
- 创建项目后直接发送事件，不使用 Outbox。
- 使用原始 UUID，不添加业务前缀。
- 只使用内存存储，不接 PostgreSQL。
- 将 Project 拆成独立微服务。

### ⑥ 为什么不选其他方式

- `create_all()` 无法可靠管理后续数据库变更。
- `main.py` 或 `services.py` 会破坏一个概念一个模块。
- 直接发事件可能导致项目存在但事件丢失。
- 原始 UUID 不利于日志追踪和外部接口辨识。
- 内存存储在服务重启后丢数据。
- 微服务对当前单机 MVP 过重，会增加网络、部署和调试成本。

### ⑦ 这种方式的难点是什么

- Docker 启动时可靠执行数据库迁移。
- 保证项目与 Outbox 同事务提交。
- 防止模块通过内部文件互相导入。
- 集成测试中隔离 PostgreSQL 和其他依赖。
- 保持现有 M0 服务和前端不回归。

### ⑧ 怎么能克服这种难点

- 在 Compose 中增加一次性 `migrate` 服务，API 和 Worker 等待迁移完成。
- 在同一个 SQLAlchemy Session 中写入 Project 和 Outbox。
- 使用 `public.py` 和导入检查限制模块边界。
- 使用独立测试数据库并回滚测试事务。
- 改动前运行健康基线，改动后运行 pytest、Compose 和健康检查。
- 每个切片独立提交，保留回滚点。

### M1-12A.1：完成后换模板重新生成修复

#### 一、目标

第一版视频完成后，如果最新配音和字幕仍为已确认状态，可以直接更换有人/无人模式或无人模板重新生成，不再被 Pipeline 的 completed 状态误拦截。

#### 二、边界

本次要做：

- 允许从 `audio_subtitle_confirmed`、`video_plan_ready`、`completed`、`failed` 创建新视频方案。
- 视频正在生成时拒绝重复创建方案。
- 最新配音或字幕未确认时返回准确提示。
- 验证连续生成两版不同模板，旧成片对象不被覆盖。

本次不做：

- 不新增接口和数据库迁移。
- 不自动确认配音或字幕。
- 不改变 Wan、Shotstack 和视频编码链路。

#### 三、切片

逻辑：先判断视频是否正在生成，再判断 Pipeline 是否处于可重新生成状态，最后校验最新配音和字幕是否已确认。

工具：继续复用现有 Job、Outbox、ObjectStorage 和 Pipeline Public Service。

返回：正在生成时返回明确的忙碌提示；最新配音或字幕未确认时返回具体的确认提示。

测试：集成测试连续生成 clean、dynamic 两版，断言两个 Output 独立存在且第一版对象仍可读取；前端测试验证后端原因能够显示。

#### 八段总结

① 解决了什么：解决首版成片完成后无法换模板再生成的问题。

② 怎么实现的：把 Pipeline 的“可重新生成状态”和“视频忙碌状态”分开判断。

③ 具体的实现方式：后端增加状态白名单，先拦截生成中状态，再校验最新配音和字幕确认状态；前端展示具体错误原因。

④ 为什么选择这种方式：改动集中、与现有状态机一致、不会自动确认用户内容。

⑤ 有没有其他方式：新增专用重新生成接口、自动沿用上一版已确认配音字幕。

⑥ 为什么不选其他方式：新增接口重复现有能力；自动沿用可能让未确认的新配音字幕被误解为已经生效。

⑦ 这种方式的难点是什么：区分视频已完成、视频处理中、配音字幕未确认三类状态。

⑧ 怎么能克服这种难点：将状态拆分常量并用连续生成回归测试覆盖。

#### 八段总结

① 解决了什么：解决真实合成 Provider 无法替换的问题。

② 怎么实现的：增加 Composition Port，将本地 Mock 与 Shotstack 实现隔离。

⑧ 怎么能克服这种难点：Fake HTTP 契约测试、直传素材、轮询超时、最终 MP4 校验和分阶段真实烟测。

#### ① 解决了什么

#### ② 怎么实现的

在更高分辨率画布上完成推近，再一次性缩回目标分辨率，让输出层的位移变化小于一个像素。

#### ③ 具体的实现方式

`dynamic` 商品模式将画布设为目标尺寸的 2 倍；`zoompan` 在 2 倍画布上执行 `1.0 → 1.05` 的线性缩放；结束后用 `scale=目标宽:目标高:flags=lanczos` 回到原输出规格。

#### ④ 为什么选择这种方式

改动范围小，不增加供应商和费用，不改变上下游接口，且可以直接复用现有 FFmpeg 和测试体系。

#### ⑤ 有没有其他方式

一是使用 Shotstack 原生 `zoomIn`；二是继续在 1 倍画布调 `zoompan` 坐标；三是取消推近；四是引入专门的视频合成 SDK。

#### ⑥ 为什么不选其他方式

Shotstack 原生动画需要额外真实渲染烟测；1 倍画布不能消除像素级跳变；取消推近不满足需求；引入新 SDK 会扩大依赖和回归范围。

#### ⑦ 这种方式的难点是什么

2 倍画布会增加单次 FFmpeg 渲染计算量，且“抖动是否消失”最终需要人工视频验收。

#### ⑧ 怎么能克服这种难点

限制改动只发生在 `dynamic` 商品模板，保留现有编码参数；用单元测试验证推近和超采样路径，再用真实成片人工确认。若仍抖动，再切换 Shotstack 原生 `zoomIn`，不继续微调 `zoompan`。

解决真实链路默认未启用、provider 混用时可能静默产生错误结果，以及 Shotstack 临时断连导致任务失败的问题。

#### ② 怎么实现的

用显式开关和完整配置校验控制真实链路，并在 Shotstack Adapter 内增加有限网络重试。

#### ③ 具体的实现方式

检查 image_edit、wan_i2v、composition、API Key 和模型配置；对 httpx.TransportError 做指数退避重试，其他错误立即失败。

#### ④ 为什么选择这种方式

配置校验避免错误回退，重试只处理可恢复网络问题，不掩盖真实业务失败。

#### ⑤ 有没有其他方式

继续手动脚本运行；默认打开真实 Provider；对全部异常无限重试；失败后回退 Mock。

#### ⑥ 为什么不选其他方式

手动脚本无法服务 UI；默认打开会误用付费接口；无限重试会卡死任务；回退 Mock 会生成错误成片。

#### ⑦ 这种方式的难点是什么

需要区分临时网络错误和真实 Provider 错误，并确保重试期间不会重复提交渲染任务。

#### ⑧ 怎么能克服这种难点

只重试传输层异常，重试次数和退避可配置；提交渲染请求保持幂等，测试覆盖首次失败后成功和连续失败。

## 八段总结

### ① 解决了什么

解决商品图片从浏览器进入系统并成为可追踪 Asset 的问题，为识别和主图处理提供稳定输入。

### ② 怎么实现的

使用 `asset` 模块管理素材生命周期，使用 `object_storage` 集成模块封装 MinIO。浏览器通过预签名 URL 直传，API 在完成阶段重新验证文件，并通过 Outbox 写入 `AssetRegistered`。

### ③ 具体的实现方式

预签名接口创建 `pending` Asset，返回短期 PUT URL。浏览器直接上传 MinIO。完成接口读取对象、校验大小和 SHA-256、用 Pillow 验证格式与尺寸，更新 Asset 为 `ready`，并在同一事务写 Outbox。

### ④ 为什么选择这种方式

直传避免大文件经过 FastAPI。服务端复核不信任客户端声明。独立 Asset 模块和存储 Adapter 保证修改 MinIO、上传策略或图片规则时不会影响 Project 和 Outbox。

### ⑤ 有没有其他方式

有其他方式：

- FastAPI 接收 multipart 后转发到 MinIO。
- 先上传临时目录，再后台同步。
- 完全信任浏览器提供的尺寸和摘要。
- 使用本地文件系统。
- 上传完成后再创建 Asset。
- 在 Asset 服务中直接使用 MinIO SDK。

### ⑥ 为什么不选其他方式

- API 中转大文件会占用内存和请求时间。
- 临时目录增加一致性和清理问题。
- 信任客户端无法保证文件真实性和安全性。
- 本地文件不适合多 Worker。
- 不保留 `pending` 会产生孤儿文件。
- 直接使用 MinIO SDK 会形成强耦合。

### ⑦ 这种方式的难点是什么

- 预签名 URL 的 Host 必须对浏览器可访问。
- 流式计算 SHA-256 和读取图片要避免多次传输。
- CORS 必须允许浏览器 PUT。
- 并发上传不能突破 5 张限制。
- 素材状态和 Outbox 必须同事务。
- Pending 文件需要后续清理入口。

### ⑧ 怎么能克服这种难点

- 内部使用 `minio:9000`，签名 URL 使用 `MINIO_PUBLIC_ENDPOINT`，测试通过依赖覆盖使用内部地址。
- 在同一个对象流中计算哈希并交给 Pillow 解析。
- 使用 MinIO CORS 配置明确来源、方法和请求头。
- 在事务内检查数量，并增加数据库唯一约束。
- Asset 状态和 Outbox 使用同一 SQLAlchemy Session。
- M1-03 再实现过期清理。

## 八段总结

### ① 解决了什么

### ⑦ 这种方式的难点是什么

## M3-02：Agent 思考计时按轮次归零

### 状态

- 用户确认：是
- 实施状态：已完成
- 用户验收：已通过

### 一、目标

让每次发送新消息后，思考计时都从 `0 秒` 重新开始并每秒递增；助手回复后停止显示，下一轮再次从 `0` 开始。

### 二、边界

做：修正前端计时起点，补充“上一轮计时不得延续到下一轮”的回归测试。
不做：不改 MiniClaw 后端、不改消息接口、不改思考卡片样式、不读取或修改 `.env`。

### 三、切片

接口：不新增接口，仅在 Agent 会话组件内记录本次发送时间。
逻辑：点击发送时先记录本地时间，等待期间优先使用该时间作为计时起点；刷新页面导致本地状态丢失时，才回退到最近一条用户消息时间。
工具：沿用现有每秒定时器。
返回：计时秒数按 `max(0, now - 本轮发送时间) / 1000` 取整。
测试：覆盖普通等待、回复后隐藏、上一轮已等待很久后下一轮从零开始，以及连续两轮分别归零。

### 四、涉及文件

- 修改 `web/src/features/agent/AgentConversation.tsx`
- 修改 `web/src/features/agent/AgentConversation.test.tsx`
- 记录 `D:\download new\ai_coding\0ne Take\docs\方案档案.md`

### 五、验收标准

- 新消息发出后立即显示 `已等待 0 秒`。
- 每过 1 秒显示值增加 1。
- 不再继承上一轮思考时长。
- 助手回复后思考卡片消失。
- 再发下一条消息重新从 `0 秒` 开始。
- 定向测试和前端构建通过。

### 六、待拍板参数

- 计时起点采用用户点击发送时的本地时间，而非服务器收到消息的时间；正常误差小于 1 秒。
- 已确认按此方式实施。

### 八段总结

① 解决了什么：新请求继承上一轮思考时长的问题。

② 怎么实现的：发送前先记录本轮计时起点，不再依赖尚未写入消息列表的新消息。

③ 具体的实现方式：Agent 会话组件保存 `sendStartedAt`，思考卡片优先使用该值；页面刷新后没有本地值时，回退到最近一条用户消息时间。

④ 为什么选择这种方式：改动最小，直接对应点击发送动作，并能覆盖请求尚未返回、消息列表尚未刷新这段空窗期。

⑤ 有没有其他方式：乐观插入用户消息、由后端返回 `runStartedAt`、只依赖 WebSocket 的首条消息事件。

⑥ 为什么不选其他方式：乐观消息需要处理去重和失败回滚；后端改动接口范围更大；WebSocket 事件可能延迟或缺失，仍会出现计时不稳定。

⑦ 这种方式的难点是什么：组件内状态在页面刷新后会丢失，且发送失败时需要清理本轮状态。

⑧ 怎么能克服：刷新后使用最近用户消息时间作为回退；发送失败时清空本轮起点；回复到达并隐藏卡片后重置状态。
