# One Take 商品 AI 视频生成 MVP 架构设计

> 文档版本：v1.0  
> 文档状态：架构基线  
> 更新时间：2026-09-17  
> 首版定位：内部演示 MVP  
> 核心技术路线：无 Coze 依赖、模块化单体、事件驱动 Pipeline、端口与 Adapter 隔离供应商

---

## 1. 文档目标

本文档用于固化 One Take 商品 AI 视频生成 MVP 的架构设计，并作为后续开发、评审、测试和部署的统一依据。

架构重点解决的问题：

1. 明确每个业务概念的归属模块，做到“一个概念一个模块”。
2. 修改一个功能时，不修改职责无关的模块。
3. 替换 AI、图像、语音、视频或云合成供应商时，不影响业务流程代码。
4. 支持每一步预览、编辑、确认后再继续。
5. 支持语音和字幕两个独立开关的四种组合。
6. 支持失败重试、人工确认、成本控制和 24 小时媒体清理。
7. 保证生成失败时不会把异常结果标记为完成。

本文档覆盖：

- 系统上下文和运行架构。
- 前端、后端、平台和供应商模块。
- 模块依赖规则和数据所有权。
- Pipeline 状态机与领域事件。
- Qwen、Photoroom、CosyVoice、Wan、Shotstack 的接入方式。
- Redis 异步任务、失败隔离、契约版本和部署方式。
- Pipeline 与 Boss-Worker 的选型决策。

不在本文档范围内：

- 页面视觉稿。
- 具体 SQL 建表语句。
- 供应商接口的逐字段映射。
- 生产级多租户、计费和权限系统。

## 2. 架构决策摘要

| 编号 | 决策 | 说明 |
|---|---|---|
| ADR-001 | 不依赖 Coze | Coze 可以作为未来可选 Prototype Adapter，但不是当前核心依赖 |
| ADR-002 | 模块化单体 | 一个部署单元内按业务边界严格分模块，不立即拆微服务 |
| ADR-003 | 事件驱动 Pipeline | 使用确定性状态机推进固定业务流程 |
| ADR-004 | Pipeline 优先，Boss-Worker 后置 | MVP 不做动态自主规划，未来通过 PlannerPort 扩展 |
| ADR-005 | 端口与 Adapter | 业务模块只依赖 Port，供应商实现放在独立 Adapter |
| ADR-006 | 一个概念一个模块 | 禁止创建覆盖多个概念的 `common`、`utils` 或 `ai_service` 大模块 |
| ADR-007 | 数据所有权隔离 | 每个模块拥有自己的 Schema 或数据表，禁止跨模块直接访问 ORM 和表 |
| ADR-008 | 事件 Outbox | 模块状态和待发布事件在同一事务中写入，保证不丢事件 |
| ADR-009 | 独立任务队列 | 识别、抠图、配音、视频和渲染使用独立队列，故障相互隔离 |
| ADR-010 | 对象存储为媒体交换层 | 云服务通过短期签名 URL 获取输入和输出媒体 |
| ADR-011 | 版本化契约 | API 和事件均包含版本，破坏性变更必须新增版本 |
| ADR-012 | 幂等命令 | 所有耗时操作必须携带幂等键，避免重复扣费和重复生成 |

## 3. 架构原则

### 3.1 一个概念一个模块

每个模块只能表达一个业务概念，例如：

- 识别是 `recognition`。
- 图像编辑是 `image_edit`。
- 抠图是 `matting`。
- 配音是 `voice`。
- 字幕是 `subtitle`。
- 云合成是 `composition`。
- 渲染是 `render`。

不允许出现：

```text
ai_service.py
image_utils.py
common.py
helpers.py
business_service.py
```

这些模块通常会同时承载多个概念，最终变成强耦合中心。

### 3.2 改一个功能时不影响其他功能

变更隔离依赖以下机制共同实现：

1. 模块只依赖公开 Port。
2. 供应商只存在于 Adapter 模块。
3. 模块间只通过公开 API 和领域事件通信。
4. 每个模块拥有自己的数据。
5. API 和事件向后兼容。
6. 每个耗时任务独立队列、超时、重试和熔断。
7. 新功能使用 Feature Flag。
8. 修改上游数据后，通过 `StepInvalidated` 作废下游产物，不直接修改其他模块内部状态。
9. 新 Provider 先影子运行，再切换流量。
10. 契约测试在 CI 中阻止不兼容变更。

注意：

> “完全不影响”不能只靠架构口号保证。必须配合模块边界检查、契约测试、幂等和版本管理。

### 3.3 人工确认优于全自动推进

识别、主图、文案、声音字幕和视频设置均属于人工确认节点。

Pipeline 在这些位置进入：

```text
WAITING_USER_CONFIRMATION
```

只有用户确认后才发布下一步命令。

### 3.4 失败不得伪装成成功

任何步骤只有满足以下条件才能进入成功状态：

- 任务返回了有效产物。
- 产物已经通过格式和完整性校验。
- 下游所需字段满足契约。
- 结果已经被持久化或登记到对象存储。

## 4. 系统上下文

```text
用户
  │
  ▼
One Take 响应式 Web
  │
  ▼
FastAPI API / BFF
  │
  ├── Pipeline / 状态机
  ├── 业务模块
  ├── Redis / RQ Worker
  └── PostgreSQL
          │
          ▼
      对象存储
          │
          ├── Qwen-VL-Plus
          ├── Qwen-Image-Edit-Plus
          ├── Photoroom
          ├── CosyVoice V2
          ├── Wan S2V
          ├── Wan2.6 I2V
          └── Shotstack
```

### 外部角色

| 角色 | 作用 |
|---|---|
| 用户 | 上传素材、确认主体、编辑文案、选择设置、下载结果 |
| 前端 | 交互、状态展示、文件选择、进度和错误提示 |
| FastAPI | API、业务用例、Pipeline 推进、鉴权和签名 URL |
| Worker | 执行长任务和供应商调用 |
| PostgreSQL | 保存模块状态、确认记录、任务和事件 Outbox |
| Redis | 队列、任务进度、临时锁和重试元数据 |
| 对象存储 | 输入图、中间产物、音频、字幕、视频和导出 |
| AI/媒体供应商 | 提供识别、编辑、抠图、语音、视频和云合成能力 |

```text
┌──────────────────────────────────────┐
│ React Web                            │
│  input / recognition / main-image    │
│  script / audio / video / output     │
└──────────────────┬───────────────────┘
                   │ HTTPS
┌──────────────────▼───────────────────┐
│ FastAPI API                         │
│  - Project API                      │
│  - Pipeline Commands                │
│  - Query Views                      │
│  - Signed URL Service               │
└──────────┬────────────────┬──────────┘
           │                │
           │                │
┌──────────▼───────┐  ┌─────▼──────────┐
│ PostgreSQL       │  │ Redis + RQ     │
│ Module Schemas    │  │ Per-Queue Jobs │
│ Outbox Events     │  │ Locks / Status │
└──────────┬───────┘  └─────┬──────────┘
           │                │
           └────────┬───────┘
                    ▼
┌──────────────────────────────────────┐
│ Worker Pools                         │
│ recognition / image_edit / matting    │
│ voice / subtitle / avatar_video       │
│ product_video / render                │
└──────────────────┬───────────────────┘
                   ▼
┌──────────────────────────────────────┐
│ Provider Adapters                    │
│ Qwen / Photoroom / CosyVoice / Wan   │
│ Shotstack / Object Storage            │
└──────────────────────────────────────┘
```

### 运行单元

| 单元 | 职责 |
|---|---|
| `web` | 用户交互和前端流程 |
| `api` | HTTP API、确认命令、查询和事件调度 |
| `worker` | 长任务和供应商调用 |
| `scheduler` | Outbox 发布、超时检测、媒体清理 |
| `postgres` | 模块状态和事件记录 |
| `redis` | 队列、锁和短期状态 |
| `object-storage` | 媒体文件和签名 URL |

MVP 推荐部署为一个 API 容器、一个 Worker 镜像和若干个 Queue Worker 进程，不拆微服务。

## 6. 核心设计结论

1. Pipeline 是主控制面，不是供应商调用器。
2. 业务模块是 Worker，但每个 Worker 只处理自己的概念。
3. Provider Adapter 是唯一允许接触外部 SDK 的位置。
4. 一个模块一个数据所有权边界。
5. 业务事件负责推进流程，公开 API 负责查询和人工确认。
6. 语音和字幕是独立分支，不使用单一布尔值合并。
7. Qwen-Image-Edit-Plus 必须在 Photoroom 之前执行，避免透明通道被破坏。
8. Wan2.6 I2V 只负责运动和背景，原始主图由 Shotstack 叠加，防止商品变形。
9. Wan S2V 只生成数字人口播片段，最终商品和字幕由 Shotstack 合成。
10. Pipeline 之外预留 PlannerPort，未来可以增加 Boss，但不进入 MVP 主链路。

## 8. 前端模块

### 8.1 模块职责

| 模块 | 单一概念 | 主要职责 |
|---|---|---|
| `project-shell` | 项目壳 | 路由、顶部导航、项目上下文、全局 Toast |
| `input` | 素材输入 | 多图上传、格式校验、商品名称和补充说明 |
| `recognition` | 商品识别 | 候选展示、主体选择、确认和重试 |
| `main-image` | 主图 | 图像编辑、抠图、透明背景预览和确认 |
| `script` | 文案 | 事实补充、生成、编辑、重新生成和确认 |
| `audio-subtitle` | 声音字幕 | 语音和字幕独立开关、音色、语速、试听、字幕编辑 |
| `video-settings` | 视频设置 | 有人/无人模式、模板、输出规格确认 |
| `output` | 成片 | 9:16 预览、播放、下载、失败原因 |
| `jobs` | 任务状态 | 队列、处理中、等待确认、完成、失败和取消 |

### 8.2 前端隔离规则

每个前端模块拥有：

- 自己的组件目录。
- 自己的 API Client。
- 自己的表单状态。
- 自己的 TypeScript 类型。
- 自己的错误边界。
- 自己的单元测试。

禁止：

- 建立一个 `globalStore` 保存所有业务状态。
- 在视频设置模块中直接修改文案。
- 在识别模块中直接调用 Photoroom。
- 在公共组件中写供应商特有逻辑。
- 通过组件 props 传完整的后端响应对象。

前端共享层只允许包含：

- 设计 Token。
- 基础按钮、输入框和弹层。
- 项目上下文 ID。
- 任务状态展示组件。
- 通用错误呈现组件。

### 9.1 项目生命周期模块

| 模块 | 单一概念 | 拥有的数据 |
|---|---|---|
| `project` | 项目 | 项目基本信息、状态、过期时间、当前版本 |
| `asset` | 输入素材 | 图片对象、格式、尺寸、大小、哈希和签名 URL |
| `retention` | 数据保留 | 删除时间、清理任务、用户主动删除 |

### 9.2 图片链路模块

| 模块 | 单一概念 | 拥有的数据 |
|---|---|---|
| `recognition` | 商品识别 | 识别任务、候选主体、置信度、用户确认 |
| `image_edit` | 图像编辑 | 编辑任务、清理前后对象、外部字卡检测结果 |
| `matting` | 抠图 | 抠图任务、透明图和供应商任务 ID |
| `main_image` | 主图成品 | 画布参数、透明母版、白底导出 |

处理顺序必须为：

```text
recognition
→ image_edit
→ matting
→ main_image
```

原因：

- Qwen-Image-Edit-Plus 处理 RGB 图像更稳定。
- Photoroom 最后执行，避免 Qwen 编辑破坏透明通道。
- 主图标准化最后执行，保证 2000×2000 和 1000×1000 输出规格。

### 10.0 Provider 运行模式

每项能力使用独立 Provider 模式：

```text
RECOGNITION_PROVIDER=mock|real
IMAGE_EDIT_PROVIDER=mock|real
MATTING_PROVIDER=mock|real
SCRIPT_PROVIDER=mock|real
```

`MOCK_PROVIDERS=true` 是全局安全锁，开启后所有能力强制 Mock。真实 Provider 缺少 Key 或调用失败时不自动回退 Mock。

### 10.1 Qwen-VL-Plus

使用两个独立适配器：

```text
QwenRecognitionAdapter
QwenCopywritingAdapter
```

同一个供应商模块允许实现两个端口，但两者必须有独立请求模型、响应模型和错误转换。

识别输出必须为结构化 JSON：

```json
{
  "candidates": [
    {
      "candidate_id": "cand_001",
      "label": "榨汁杯",
      "confidence": 0.91,
      "bbox": [0.12, 0.18, 0.72, 0.84],
      "visible_text": []
    }
  ],
  "ambiguous": false,
  "error": null
}
```

文案输出必须包含事实引用：

```json
{
  "script": "……",
  "claims": [
    {
      "text": "轻巧杯身",
      "source_fact_id": "selling_point_1"
    }
  ],
  "unresolved_claims": []
}
```

任何没有用户确认依据的卖点不能进入最终文案。

### 10.2 Qwen-Image-Edit-Plus

职责：

- 去除外部促销字卡。
- 去除无关主体。
- 处理可恢复的遮挡。
- 保留商品包装文字和关键外观。

不负责：

- 最终透明 PNG。
- 最终正方形画布。
- 最终文件大小压缩。

### 10.3 Photoroom

职责：

- 对 Qwen 编辑后的图片做去背。
- 输出透明 PNG。
- 返回供应商任务 ID 和结果 URL。

接入要求：

- 验证透明通道。
- 验证输入 URL 有效期。
- 验证输出下载 URL。
- 记录供应商失败码。
- 失败不能覆盖上一版主图。

### 10.4 CosyVoice V2

职责：

- 根据最终确认文案生成配音。
- 支持音色、语速和语言。
- 返回音频对象和音频时长。

不负责：

- 生成字幕文本。
- 判断字幕是否显示。
- 视频合成。

### 10.5 Wan S2V

只负责：

```text
数字人形象 + 配音音频
→ 口播视频片段
```

最终成片中的商品、字幕、品牌字卡和构图由 Shotstack 合成。

### 10.6 Wan2.6 I2V

只负责：

```text
商品主图
→ 背景运动、镜头运动和商品动效片段
```

最终视频必须叠加原始高保真主图，防止生成模型改变商品外观。

### 10.7 Shotstack

负责：

- 组合视频片段、主图、音频和字幕。
- 处理 9:16 和 1080×1920。
- 渲染最终 MP4。
- 返回 Render Job 和下载地址。

合成和渲染必须拆成两个模块：

```text
composition
  → 生成时间轴 JSON

render
  → 提交 Shotstack 并跟踪任务
```

这样更改模板只影响 `composition`，更换渲染供应商只影响 `render`。

## 12. Pipeline 状态机

### 12.1 Pipeline 的职责

`pipeline` 是主控制面，负责：

- 判断当前步骤。
- 校验前置条件。
- 发布下一步命令。
- 等待人工确认。
- 处理步骤失效。
- 记录失败和可恢复点。

`pipeline` 不负责：

- 调用 Qwen。
- 调用 Photoroom。
- 调用 CosyVoice。
- 调用 Wan。
- 调用 Shotstack。
- 解析供应商原始响应。
- 生成文案或字幕。

### 12.2 主状态流

```text
draft
→ recognizing
→ recognition_confirmed
→ image_editing
→ image_edit_completed
→ matting
→ matting_completed
→ main_image_ready
→ main_image_confirmed
→ script_ready
→ script_confirmed
→ voice_ready
→ subtitle_ready
→ video_plan_confirmed
→ video_generating
→ video_ready
→ composition_ready
→ rendering
→ completed
→ failed
```

### 12.3 条件分支

识别确认后进入主图链路：

```text
recognition_confirmed
→ image_editing
→ matting
→ main_image
```

文案确认后并行进入：

```text
script_confirmed
  ├── voice
  └── subtitle
```

语音和字幕开关：

```text
voiceOn=true  → voice
voiceOn=false → 跳过 voice，记录 VoiceSkipped

subtitleOn=true  → subtitle
subtitleOn=false → 跳过 subtitle，记录 SubtitleSkipped
```

视频模式：

```text
videoMode=human   → avatar_video
videoMode=product → product_video
```

合成输入：

```text
CompositionInput =
  videoAsset
  + mainImage
  + optional audio
  + optional captions
  + template
```

### 12.4 用户确认门

Pipeline 必须在以下节点暂停：

| 节点 | 用户动作 |
|---|---|
| `recognition_completed` | 选择正确主体或重新识别 |
| `main_image_ready` | 检查边缘、包装文字和遮挡 |
| `script_ready` | 编辑、重新生成或确认 |
| `audio_subtitle_ready` | 设置音色、语速、字幕和开关 |
| `video_plan_ready` | 选择模式、模板和输出参数 |
| `render_completed` | 预览、下载或重新生成 |

### 12.5 下游失效规则

上游修改后，Pipeline 只能发布失效事件，不能直接修改下游模块的数据。

| 修改内容 | 失效范围 |
|---|---|
| 更换输入素材 | 识别、图像编辑、抠图、主图、视频、合成、渲染 |
| 更换识别主体 | 图像编辑、抠图、主图、视频、合成、渲染 |
| 修改主图 | 视频、合成、渲染 |
| 修改文案 | 语音、字幕、视频、合成、渲染 |
| 修改语音设置 | 语音、合成、渲染 |
| 修改字幕内容 | 字幕、合成、渲染 |
| 修改视频模式或模板 | 视频、合成、渲染 |
| 只修改云合成模板 | 合成、渲染 |

失效只标记下游为 `STALE`，不直接删除历史产物。用户确认重新生成后才能产生新版本。

- 已完成产物。
- 失败原因。

## 22. Pipeline 与 Boss-Worker 决策

### 22.1 为什么选择 Pipeline

当前产品的流程是确定性流程：

- 输入固定。
- 图片处理顺序固定。
- 文案、语音和字幕依赖关系明确。
- 有人/无人视频是条件分支。
- 每个关键节点需要人工确认。
- 输出规格和成本约束明确。

Pipeline 的优势：

- 状态可追踪。
- 失败可恢复。
- 成本可控制。
- 用户确认点清晰。
- 供应商可以替换。
- 测试用例明确。
- 不会出现 Agent 自主跳过确认或重复调用高价模型。

### 22.2 为什么不先用 Boss-Worker

Boss-Worker 适合开放式和动态规划任务，不适合当前 MVP 的主要原因：

1. 任务图基本固定，动态规划收益低。
2. 自主调度难以可靠暂停在两个人工确认点之间。
3. 多次生成视频容易导致成本失控。
4. Boss 可能成为新的耦合中心。
5. 失败恢复和审计难度更高。
6. 当前需求不需要多 Agent 讨论或自动选路。

### 22.3 未来扩展方式

保留扩接口：

```text
PlannerPort
CapabilityRegistry
WorkerRegistry
ProviderSelectionPolicy
BudgetPolicy
```

当出现以下需求时，再加入 Boss：

- 自动比较多个模型。
- 根据商品类型动态选择工作流。
- 生成多个文案和视频方案。
- 自动选择成本和质量之间的平衡。
- 视频失败后自动切换供应商。
- 多商品批量并行生产。

混合模式：

```text
Boss / Planner
  ├── Pipeline A：识别 → 编辑 → 抠图 → 主图
  ├── Pipeline B：文案 → 语音 → 字幕
  └── Pipeline C：视频生成 → 合成 → 渲染
```

Boss 只选择 Pipeline，不直接调用供应商。

## 23. 关键风险

| 风险 | 影响 | 处理方式 |
|---|---|---|
| Qwen-Image-Edit-Plus 改变包装文字 | 主图不准确 | 编辑前后 OCR/像素对比，用户确认 |
| Photoroom 复杂边缘失败 | 主图质量下降 | 保留上一版，允许重新抠图或换 Provider |
| CosyVoice 与字幕时间轴不一致 | 音画不同步 | 以最终音频时长重新切分字幕 |
| Wan S2V 授权或适配不通过 | 有人模式受阻 | 先做技术 Spike，保留 Adapter 替换 |
| Wan2.6 I2V 改变商品 | 商品不一致 | Shotstack 叠加原始主图 |
| Shotstack 渲染失败 | 无成片 | 独立 render 队列，不覆盖主图和音频 |
| 云服务 URL 过期 | 任务失败 | 使用足够时效的签名 URL，调用前刷新 |
| 24 小时删除冲突 | 问题难复现 | 保存不含媒体的错误日志和输入摘要 |
| 重试成本过高 | 预算失控 | 幂等键、并发限制、成本告警和用户确认 |

## 25. 最终架构定义

> One Take MVP 采用模块化单体、事件驱动 Pipeline、端口与 Adapter、独立数据所有权和独立任务队列。Pipeline 负责确定性状态推进，各业务模块负责单一能力，供应商 Adapter 负责外部服务接入。一个概念一个模块，一个功能一个边界，一个失败一个独立恢复点。

核心架构不变式：

1. 不改供应商 SDK，不跨模块修改业务模块。
2. 不跨模块写表，不共享 ORM Model。
3. 不把供应商响应直接传给前端。
4. 不在 Pipeline 中写供应商参数。
5. 不在用户确认前自动进入高成本视频生成。
6. 不在失败时把下游结果标记为成功。
7. 不让语音和字幕开关互相影响。
8. 不让新 Provider 修改旧 Provider 的业务契约。

以上内容作为 One Take 后续开发、测试、部署和评审的架构基线。
